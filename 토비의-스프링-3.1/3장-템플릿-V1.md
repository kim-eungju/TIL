## 1. 시작은 JDBC 예제
JDBC 예제
```java
Connection c = null;
PreparedStatement ps = null;

try {
    c = dataSource.getConnection();
    ps = c.prepareStatement("delete from users");

} catch (SQLException e) {
    throw e;
} finally {

    if (ps != null) {
        try {
            ps.close();
        } catch (SQLException e) {}
    }

    if (c != null) {
        try {
            c.close();
        } catch (SQLException e) {}
    }
}
```
```
Connection 획득	
	↓
PreparedStatement 생성
	↓
SQL 실행
	↓
예외 처리
	↓
리소스 반환
```

>무엇이 변하고, 무엇이 변하지 않는가?

---

## 2. 변하는 것과 변하지 않는 것을 분리

변하지 않는 흐름과 변하는 로직을 분리한다.
```
[변하지 않는 작업 흐름]

Connection 획득
       ↓
PreparedStatement 생성 ← [변하는 로직]
       ↓
실행
       ↓
예외 처리
       ↓
리소스 반환
```
즉,
> 변하지 않는 흐름과 변하는 로직을 분리한다.

이걸 구현하기 위해 여러 디자인 패턴을 거쳐간다.

---

## 3. 템플릿 메소드 패턴

첫 번째 시도.
상속을 이용해서 변하는 부분만 하위 클래스에게 맡긴다.
```java
abstract class UserDao {

    protected abstract PreparedStatement makeStatement(
            Connection c) throws SQLException;

    public void deleteAll() throws SQLException {

        Connection c = dataSource.getConnection();

        PreparedStatement ps =
                makeStatement(c);

        ps.executeUpdate();

        ps.close();
        c.close();
    }
}
```
하위 클래스
```java
class DeleteAllUserDao extends UserDao {

    @Override
    protected PreparedStatement makeStatement(Connection c)
            throws SQLException {

        return c.prepareStatement(
                "delete from users"
        );
    }
}
```
구조는
```
UserDao
  │
  ├─ 공통 처리
  │
  └─ makeStatement()
          ↑
     하위 클래스 구현
```
하지만 단점이 있다.
__SQL 하나 바꾸려고 클래스를 계속 만들어야함.__
그래서 다음 단계로 넘어간다.

## 4. 전략 패턴 ⭐

3장의 핵심 포인트
변하는 부분을 인터페이스로 분리한다.
```java
public interface StatementStrategy {

    PreparedStatement makePreparedStatement(
            Connection c) throws SQLException;
}
```
구현체
```java
public class DeleteAllStatement
        implements StatementStrategy {

    @Override
    public PreparedStatement makePreparedStatement(
            Connection c) throws SQLException {

        return c.prepareStatement(
                "delete from users"
        );
    }
}
```
그리고 공통 흐름은 전략을 받아서 실행한다.
```java
public void jdbcContextWithStatementStrategy(
        StatementStrategy strategy)
        throws SQLException {

    Connection c = dataSource.getConnection();

    PreparedStatement ps =
            strategy.makePreparedStatement(c);

    ps.executeUpdate();

    ps.close();
    c.close();
}
```
사용
```java
StatementStrategy strategy =
        new DeleteAllStatement();

jdbcContextWithStatementStrategy(strategy);
```

## 5. 그런데 전략 클래스 만드는 것도 귀찮다

전략 패턴은 좋은데 이런 클래스가 계속 생긴다
```
DeleteAllStatement
AddStatement
UpdateStatement
...
```

SQL 하나 실행하려고 클래스를 하나 만드는 건 좀 과하다
그래서 책에서는
```
전략 클래스
	↓
로컬 클래스
	↓
익명 내부 클래스
```
로 계속 줄여나간다.
```java
jdbcContextWithStatementStrategy(
    new StatementStrategy() {

        @Override
        public PreparedStatement makePreparedStatement(
                Connection c) throws SQLException {

            return c.prepareStatement(
                    "delete from users"
            );
        }
    }
);
```
Java 8 이후 관점에서 보면 사실 이 흐름은 자연스럽게 람다로 연결된다.
```java
jdbcContextWithStatementStrategy(
    c -> c.prepareStatement(
        "delete from users"
    )
);
```

## 6. 템플릿 콜백패턴 ⭐⭐⭐
3장의 주인공이다.

책에서는 전략 패턴을 조금 특수하게 사용하는 형태를 
템플릿 콜백 패턴이라고 한다.

__Template__
전체 작업 흐름을 가진 코드
```java
Connection 획득
	↓
Callback 호출
	↓
SQL 실행
	↓
예외 처리
	↓
Resource close
```

__Callback__
그 순간에만 필요한 변하는 코드.
```java
c -> c.prepareStatement(
    "delete from users"
)
```

구조는
```
Client
   │
   │ Callback 전달
   ▼
Template
   │
   ├─ 공통 작업
   │
   ├─ callback()
   │       │
   │       └─ 변하는 작업
   │
   ├─ 예외 처리
   └─ 리소스 정리
```
> 템플릿이 전체 흐름을 제어하고, 특정 지점에서 콜백을 호출한다.

---

## 7. Spring에서 중요한 부분

Spring 곳곳에 __템플릿 콜백패턴__ 구조가 있다.
```
JdbcTemplate
TransactionTemplate
RestTemplate
RedisTemplate
JmsTemplate
```
이름에 괜히 __Template__ 이 붙은게 아니다.
대체로
```
Template

"복잡하고 반복적인 흐름은 내가 처리할게."

Callback

"개발자는 달라지는 부분만 줘."
```
라는 구조다.

> 템플릿 메서드 패턴보단 전략 패턴의 확장에 더 가깝지만, 이름은 템플릿 콜백 패턴이다.
