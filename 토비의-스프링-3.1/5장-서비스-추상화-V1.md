## 1. 사용자 레벨 업그레이드 기능

아래 코드는 사용자 조회와 순회, 승급 가능 여부 판단, 다음 등급 결정, 사용자 상태 변경, DB 저장이 하나의 메서드에 섞여 있다
```java
public void upgradeLevels() {
    List<User> users = userDao.getAll();

    for (User user : users) {
        boolean changed = false;
        // 1. 승급 조건이 반복문 안에 노출되어 있다
        if (user.getLevel() == Level.BASIC
                && user.getLogin() >= 50) {
            // 2. User의 상태를 외부에서 직접 변경한다
            user.setLevel(Level.SILVER);
            // 3. 등급을 변경할건지 기억하는 변수를 따로 사용한다
            changed = true;

        } else if (user.getLevel() == Level.SILVER
                && user.getRecommend() >= 30) {

            user.setLevel(Level.GOLD);
            changed = true;
        }

        if (changed) {
            userDao.update(user);
        }
    }
}
```
위 내용에 대해 책임을 분리해보자

코드의 양은 늘었지만 각 코드의 책임과 의도가 명확해져 변경과 테스트가 쉬워진다.
```java
// 흐름이 명확하게 읽힌다
public void upgradeLevels() {
    List<User> users = userDao.getAll();

    for (User user : users) {
        if (canUpgradeLevel(user)) {
            upgradeLevel(user);
        }
    }
}

// 사용자가 현재 등급에서 승급 가능한지를 판단한다
private boolean canUpgradeLevel(User user) {
    return switch (user.getLevel()) {
        case BASIC -> user.getLogin() >= 50;
        case SILVER -> user.getRecommend() >= 30;
        case GOLD -> false;
    };
}

// User에게 자신의 등급을 올리라고 요청한다
private void upgradeLevel(User user) {
    user.upgradeLevel();
    userDao.update(user);
}
```

        Level nextLevel = level.nextLevel();

        if (nextLevel == null) {
            throw new IllegalStateException(

트랜잭션까지 추가된 지금의 Spring 개발
```java
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;
    private final MailSender mailSender;

    @Transactional
    public void upgradeLevels() {
        List<User> users = userRepository.findAll();

        users.stream()
                .filter(User::canUpgradeLevel)
                .forEach(user -> {
                    user.upgradeLevel();
                    mailSender.send(createMessage(user));
                });
    }
}
```

## 1-1. Level 을 꼭 분리할까? (이건 상황에 따라 판단하자)

`Level`이 정말로 `User`에게만 의미가 있고 다른 도메인에서는 사용되지 않는다면, `User` 내부에 중첩 `enum`으로 두면 소속 관계가 명확해진다

```java
public class User {

    private Level level;

    public void upgradeLevel() {
        Level nextLevel = level.nextLevel();

        if (nextLevel == null) {
            throw new IllegalStateException("더 이상 승급할 수 없습니다.");
        }

        this.level = nextLevel;
    }

    public enum Level {
        GOLD(null),
        SILVER(GOLD),
        BASIC(SILVER);

        private final Level next;

        Level(Level next) {
            this.next = next;
        }

        public Level nextLevel() {
            return next;
        }
    }
}
```
외부에서는 다음처럼 사용
```java
User.Level level = User.Level.BASIC;
```

상황에 따라 판단하자
- 규모가 작고 `User` 내부에서만 사용: `User.Level`도 좋음
- 서비스, 조회 조건, 정책에서 자주 참조: 별도 `UserLevel` 타입 추천
- 향후 회원 등급 정책이 커질 가능성이 높음: 처음부터 별도 타입 추천

> 이처럼 어떤 개념을 객체 내부에 포함할지 독립된 타입으로 분리할지 고민되는 사례에서는, 해당 개념이 특정 객체의 내부 세부사항인지 애플리케이션에서 독립적으로 이야기되는 도메인 용어인지 신중하게 판단하자
