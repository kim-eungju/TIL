## 1. 핵심 흐름
> 변화하는 부분과 변화하지 않는 부분을 분리하고, 오브젝트 간 의존관계를 외부에서 설정하게 만들어라.

아래 `UserDao`의 문제는 __DB 연결 방법까지 직접 알고있다__
```java
public class UserDao {

    public void add(User user) throws SQLException {
        Connection c = DriverManager.getConnection(...);
        // SQL 실행...
    }

    public User get(String id) throws SQLException {
        Connection c = DriverManager.getConnection(...);
        // SQL 실행...
    }
}
```

```
UserDao
 ├─ 사용자 저장/조회
 └─ DB 연결 방법
```
이제 책임을 하나씩 분리해보자

---

## 2. 관심사의 분리
> 변경 되는 이유가 다른 코드는 분리하자.

`UserDao`에서 보면 DB 연결 부분을 아래 코드처럼 분리할 수 있다. 
```java
public void add(User user) {
    Connection c = getConnection();
    // 사용자 추가
}

private Connection getConnection() {
    ...
}
```
그런데 이것만으로는 부족하다.
DB 연결 방식이 회사마다 다를 수 있으니까
```
UserDao의 관심사
→ 사용자 데이터 저장/조회

Connection의 관심사
→ 어떤 DB에 어떻게 연결할 것인가
```

## 3. 상속을 이용한 분리와 그 한계

상속으로 해결해보면?
```java
public abstract class UserDao {

    public void add(User user) {
        Connection c = getConnection();
    }

    protected abstract Connection getConnection();
}
```
```java
public class NUserDao extends UserDao {

    @Override
    protected Connection getConnection() {
        // N사 DB 연결
    }
}
```
이러면 `UserDao`는 구체적인 DB 연결 방법을 몰라도 되긴 하지만, 문제가있다.

```
UserDao
   ↑
NUserDao
```
상속이라는 강한 결합이 생겨버림
Java에서는 다중 상속도 안되고, 부모-자식 관계가 강하게 묶여서 변경하기도 부담스럽다.

요약하자면
- 문제 1 : `UserDao`를 상속받아야만 Connection 기능을 사용할 수 있음
- 문제 2 : 이미 다른 클래스를 상속하고 있다면? 못씀..

즉,
```
상속
"다른 기능을 쓰려면 다른 UserDao 클래스를 만들어야 함"

조합/DI
"UserDao는 그대로 두고 넣어주는 객체만 바꾸면 됨"
```

## 4. 인터페이스를 이용한 분리

DB 연결 책임을 인터페이스로 빼보자

```java
public interface ConnectionMaker {
    Connection makeConnection();
}
```
구현체
```java
public class DConnectionMaker implements ConnectionMaker {

    @Override
    public Connection makeConnection() {
        // DB 연결
    }
}
```
`UserDao`
```java
public class UserDao {

    private ConnectionMaker connectionMaker;

    public UserDao() {
        connectionMaker = new DConnectionMaker();
    }
}
```
일단 여기까지 오면 상당히 좋아짐

```
UserDao
   ↓
ConnectionMaker
   ↑
DConnectionMaker
```

## 5. 객체가 자신의 의존성을 직접 선택하면 안 된다

이 부분이 __DI를 이해하는 핵심__이다.
`UserDao` 입장에서 생각해보면 아직 이상함
자기가 해야 할 일은

```
사용자 저장
사용자 조회
```
인데 갑자기
```java
new DConnectionMaker();
```
하면서 "나는 D사의 DB 연결 방식을 사용할 거야"라는 결정까지 하고 있음

## 6. UserDaoFactory 등장

```java
public class UserDaoFactory {

    public UserDao userDao() {
        ConnectionMaker connectionMaker =
                new DConnectionMaker();

        return new UserDao(connectionMaker);
    }
}
```
`UserDao`
```java
public class UserDao {

    private final ConnectionMaker connectionMaker;

    public UserDao(ConnectionMaker connectionMaker) {
        this.connectionMaker = connectionMaker;
    }
}
```
이게 __IoC / DI의 시작__ 이다.

## 7. 제어의 역전 IoC

원래 `UserDao`에서는 객체가 직접 다른 객체를 만들었다.
```java
public class UserDao {

    ConnectionMaker connectionMaker =
            new DConnectionMaker();
}
```
그런데 `UserDaoFactory`를 사용하면
```java
new UserDao(connectionMaker);
```
외부에서 객체를 만들어서 넣어준다.
이걸 IoC (Inversion of Control, 제어의 역전) 이라고 한다.

## 8. Spring IoC 컨테이너

이제 처음으로 Spring으로 넘어가서 위에 만든 `UserDaoFactory`를 Spring에게 맡기는것이다

예전 Spring 방식
```java
@Configuration
public class DaoFactory {

    @Bean
    public UserDao userDao() {
        return new UserDao(connectionMaker());
    }

    @Bean
    public ConnectionMaker connectionMaker() {
        return new DConnectionMaker();
    }
}
```
객체를 만들고 관계를 연결해준다.

---

## 9. Bean / BeanFactory / ApplicationContext

__Bean__ 
Spring이 생성하고 관리하는 객체
```java
@Bean
public UserDao userDao() {
    ...
}
```
여기서 만들어지는 `UserDao`가 Bean

__BeanFactory__
Bean을 생성하고 관리하는 IoC 컨테이너의 기본 기능을 정의한 인터페이스.

__ApplicationContext__
실무에서 주로 사용하는 Spring 컨테이너.
```java
ApplicationContext context =
    new AnnotationConfigApplicationContext(DaoFactory.class);
```
```java
UserDao dao =
    context.getBean("userDao", UserDao.class);
```
```
BeanFactory
   ↑
ApplicationContext
```
ApplicationContext가 BeanFactory의 기능을 포함하면서 Spring의 여러 부가 기능을 제공한다고 이해하면된다

## 10. 싱글톤 레지스트리

Spring은 기본적으로 Bean을 __Singleton Scope__로 관리한다

```java
UserDao dao1 =
    context.getBean("userDao", UserDao.class);

UserDao dao2 =
    context.getBean("userDao", UserDao.class);
```
```java
dao1 == dao2 // true
```

## 11. 싱글톤 객체는 상태를 가지면 위험하다

Bean 하나를 여러 요청이 같이 사용하니까
```java
@Service
public class UserService {

    private User user; // 위험
}
```
```
Thread A → user = 철수
Thread B → user = 영희
```

즉 Bean은 기본적으로 __Stateless하게 설계하자__
```java
@Service
public class UserService {

    public void update(User user) {
        // 지역 변수 사용
    }
}
```

## 12. 의존관계 주입 DI

`UserDao`는 `ConnectionMaker`가 필요하다.

```java
public class UserDao {

    private final ConnectionMaker connectionMaker;

    public UserDao(ConnectionMaker connectionMaker) {
        this.connectionMaker = connectionMaker;
    }
}
```
이게 __의존관계__다
```
UserDao → ConnectionMaker
```

DI는 __런타임에 실제 사용할 객체를 외부에서 연결해주는 것__이다.

코드레벨의 의존관계
```java
ConnectionMaker
```
런타임의 실제 의존관계
```java
DConnectionMaker
```
