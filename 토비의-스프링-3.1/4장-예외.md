## 1. SQLException은 어디로 갔을까?

순수 JDBC 코드 

`throws SQLException` 있음
```java
public void add(User user) throws SQLException {
    Connection c = dataSource.getConnection();
    ...
}
```
`JdbcTemplate` 을 사용하면? 

`throws SQLException` 없음
```java
public void add(User user) {
    jdbcTemplate.update(
        "insert into users(id, name) values (?, ?)",
        user.getId(),
        user.getName()
    );
}
```

`JdbcTemplate`은 `SQLException`을 어떻게 숨긴걸까?

이 질문에 답하기 위해 내용이 4장의 주제다

---

## 2. 난감한 예외처리

예외를 잡긴 잡았는데 아무것도 안 함
```java
catch (SQLException e) {
}
```

마찬가지로 아래 코드도 __예외를 처리한 게 아니다.__
```java
catch (SQLException e) {
    System.out.println(e);
}
```
```java
catch (SQLException e) {
    e.printStackTrace();
}
```

로그 한번 찍고 프로그램은 계속 정상 흐름으로 진행하고 있다

예외를 잡았으면 최소한 __복구하거나, 호출자에게 전달하거나, 의미 있는 다른 예외로 바꿔서 처리하거나__ 셋 중 하나는 하자

---

## 3. 무책임한 예외처리

무책임한 `throws Exception` 코드
```java
public void method1() throws Exception {
    method2();
}

public void method2() throws Exception {
    method3();
}

public void method3() throws Exception {
    ...
}
```
컴파일러만 만족하겠지만 호출자는 난감해진다
```java
try {
    userService.add(user);
} catch (Exception e) {
    // 그래서 뭘 처리해야 하는데?
}
```

파일 문제인지, DB 문제인지, 네트워크 문제인지, 비즈니스 문제인지 알 수가 없음

결국 체크 예외의 장점을 완전히 날려버린다

---

## 4. 예외에는 크게 세 종류가 있다

Java 예외 구조를 단순화 하면 아래와 같다

Error, 런타임예외, 체크예외 
```
Throwable
├── Error                         ← Unchecked
│   ├── OutOfMemoryError
│   └── StackOverflowError
│
└── Exception
    │
    ├── IOException               ← Checked
    │   ├── FileNotFoundException ← Checked
    │   └── EOFException          ← Checked
    │
    ├── SQLException              ← Checked
    │
    ├── ClassNotFoundException    ← Checked
    │
    ├── InterruptedException      ← Checked
    │
    └── RuntimeException          ← Unchecked
        ├── NullPointerException
        ├── IllegalArgumentException
        ├── IllegalStateException
        ├── IndexOutOfBoundsException
        └── ArithmeticException
```

## 5. 체크 예외

__"이 메서드에서 이 예외가 발생할 수 있으니, 처리하던지 위로 던지던지 해"__ 라고 강제하는 예외다.

대표적으로 JDBC의 `SQLException` 같은 예외
```java
try {
    ...
} catch (SQLException e) {
    ...
}
```
또는
```java
public void save() throws SQLException
```

---

## 6. 복구할 수 없는 체크 예외

DB 연결이 끊기는 등 __호출하는 쪽에서 복구할 방법이 없는 상황__ 이라고 해보자

`SQLException`은 체크 예외라서 컴파일러가 처리를 강제한다. 

```
DAO
 ↓ throws SQLException
Service
 ↓ throws SQLException
Controller
 ↓ throws SQLException
...
```
어차피 어느 계층에서도 복구하지 못하는데 `throws SQLException`만 계속 전파되는 문제가 생긴다.

그래서 이런 복구 불가능한 체크 예외는 런타임 예외로 전환하는 전략을 사용할 수 있다.

```java
try {
    // JDBC 작업
} catch (SQLException e) {
    throw new SomeRuntimeException(e);
}
```

---

## 7. 그래서 토비가 설명하는 예외처리 3가지 방법

1. 예외 복구

문제를 해결하고 정상 흐름으로 돌려놓는다
```java
for (int retry = 0; retry < 3; retry++) {
    try {
        connect();
        break;
    } catch (NetworkException e) {
        // 잠시 후 재시도
    }
}
```

2. 예외처리 회피

내가 처리하지 않고 나를 호출한 곳에 책임을 넘긴다
```java
public void save() throws SQLException {
    ...
}
```
또는
```java
try {
    ...
} catch (SQLException e) {
    throw e;
}
```

그런데 아무 생각 없이 `throws` 붙이는게 아니고, 

__호출자가 이 예외를 처리하는게 더 적절하다는 명확한 의도가 있어야한다__

3. 예외 전환

현재 메서드에서 문제를 해결할 수 없고, 호출자에게 넘기는 것도 적절하지 않은 경우

더 적절한 의미를 가진 예외로 바꿔서 던지자

```java
try {
    insertUser(user);
} catch (SQLException e) {
    if (isDuplicateKey(e)) {
        throw new DuplicateUserIdException(user.getId(), e);
    }

    throw e;
}
```

이렇게 되면 호출자가 훨씬 이해하기 쉬워진다

---

## 8. 예외 전환의 두 가지 목적

예제 코드

```java
try {
    insertUser(user);
} catch (SQLException e) {
    if (isDuplicateKey(e)) {
        throw new DuplicateUserIdException(user.getId(), e);
    }

    throw e;
}
```

__목적 1 의미를 명확하게 만들자__

비즈니스적으로 의미 있는 예외를 받을 수 있다
```
SQLException
      ↓
DuplicateUserIdException
```

__목적 2 체크 예외를 런타임 예외로 전환하자__ 

`RuntimeException` 상속

```java
public class DuplicateUserIdException extends RuntimeException {
    public DuplicateUserIdException(String userId, Throwable cause) {
        super("중복된 사용자 ID: " + userId, cause);
    }
}
```

## 9. 런타임 예외의 보편화

옛날 Java API에는 체크 예외가 상당히 많았다

그런데 엔터프라이즈 애플리케이션에서는 상당수 예외가 현재 코드에서 복구할 수 없는 예외다

```
DB 서버 다운
SQL 문법 오류
DB 연결 실패
잘못된 설정
서버 통신 장애
```

그래서 현대적인 프레임워크에서는 __복구 불가능한 예외를 런타임 예외로 전환하는 방식__ 을 많이 사용한다.

---

## 10. 애플리케이션 예외

애플리케이션 예외란?

은행 송금 API 에서 잔액이 부족한 경우 시스템 장애가 아니다
```
DB 죽음 ❌
버그 ❌
네트워크 장애 ❌
정상적인 비즈니스 상황 ⭕ -> 애플리케이션 예외
```

호출자는 잔액이 부족한 이 상황에 대해

```java
public void withdraw(int amount)
        throws InsufficientBalanceException {
}
```
아래와 같은 대응을 할 수 있다
```java
try {
    account.withdraw(amount);
} catch (InsufficientBalanceException e) {
    // "잔액이 부족합니다" 처리
}
```

추가로, 애플리케이션 예외 = 반드시 체크 예외 + `try/catch`"는 아니다

현대 Spring에서는 같은 의미를 런타임 예외 + 전역 예외 처리로 표현하는 경우가 많다
```java
public void withdraw(long amount) {
    if (balance < amount) {
        throw new InsufficientBalanceException("잔액이 부족합니다.");
    }

    balance -= amount;
}
```

## 11. 그래서 SQLException은 어디 갔나?

`JdbcTemplate` 을 사용하면 `throws SQLException` 없는 이유?
```java
jdbcTemplate.update(...);
```

Spring이 JDBC에서 발생한 `SQLException`을 그대로 밖으로 던지지 않고 

Spring의 `DataAccessException` 계층으로 변환해주기 때문

```java
JDBC

SQLException
     ↓
Spring이 예외 변환
     ↓
DataAccessException
     ↓
RuntimeException
```

--- 

## 12. 그런데 Spring이 한 단계 더 잘한 것

DB마다 에러 표현이 다 다를텐데 어떻게 한걸까?

Spring은 단순히 런타임 예외로 바꾸기만 한게 아니다

```
MySQL
PostgreSQL
Oracle
H2
...
```

Spring은 이런 DB별 차이를 추상화 했다
```
MySQL SQLException ───┐
Oracle SQLException ──┼──→ DuplicateKeyException
PostgreSQL SQLException ┘
```

일관된 예외 계층으로 제공한다

그래서 애플리케이션 입장에서는 특정 DB의 예외에 직접 종속될 필요가 줄어들게 된다

__구체적인 기술에 대한 종속성을 줄여주는 것__ 이게 Spring의 철학이다

## 13 최종 정리

1. 예외를 잡아서 무시하지 마라.
```java
catch (Exception e) { }
```
2. 무조건 throws Exception으로 떠넘기지도 마라.
```
throws Exception
        ↓
예외의 의미가 사라짐
```
3. 예외를 처리하는 방법은 크게 3가지
```  
복구 / 회피 / 전환
```
4. 복구할 수 없는 체크 예외라면

```
Checked Exception
        ↓
Runtime Exception으로 전환
```

5. 저수준 기술 예외는 의미 있는 예외로 추상화
```
SQLException
        ↓
DataAccessException
```
6. Spring은 이걸 이미 해준다.
```
JDBC SQLException
        ↓
Spring 예외 변환
        ↓
DataAccessException 계층
```
