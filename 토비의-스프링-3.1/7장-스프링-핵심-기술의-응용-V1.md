## 1. 역할과 구현을 분리

예를 들어 주문 서비스에 결제 코드가 직접 들어 있다고 가정해보자 <br/>
당장은 문제없지만 `OrderService`가 __토스__ 라는 구체적인 결제수단에 직접 묶여 있다

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final TossPaymentClient tossPaymentClient;

    public void order(OrderRequest request) {
        tossPaymentClient.pay(request.amount());
    }
}
```

아래와 같이 역할과 구현을 분리해보자 <br/>

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final PaymentProcessor paymentProcessor;

    public void order(OrderRequest request) {
        paymentProcessor.pay(request.amount());
    }
}
```
`OrderService`는 이제 자세한 결제 수단을 알수 없다

```java
public interface PaymentProcessor {
    PaymentResult pay(Money amount);
}
```
```java
@Component
public class TossPaymentProcessor implements PaymentProcessor {

    @Override
    public PaymentResult pay(Money amount) {
        // 토스 결제 API 호출
    }
}
```

## 2. 인터페이스는 변경 가능성이 있는 경계에 둔다

그렇다고 모든 클래스에 인터페이스를 만들라는 뜻은 아니다 <br/>
구현체가 하나이고 교체 가능성도 없는 서비스에 습관적으로 인터페이스를 만드는 건 실익이 작음 <br/>
주로 이런 경계에 인터페이스를 두자

- 외부 API
- 메시지 발행
- 파일 저장소
- 이메일, 알림 발송
- 결제 수단
- 도메인 정책
- 테스트에서 대체할 필요가 있는 의존성

```java
public interface NotificationSender {
    void send(Notification notification);
}
```
```java
@Component
public class SlackNotificationSender implements NotificationSender {
    // Slack API
}
```

비즈니스 로직은 Slack이라는 기술을 몰라도 된다

## 3. 큰 클래스는 변경 이유를 기준으로 나눈다

`AssetExcelService` 같은 서비스가 너무 많은 책임을 가지고 있다고 가정해보자
```java
@Service
public class AssetExcelService {

    public void upload(...) {
        // 파일 검증
        // 엑셀 읽기
        // 행 파싱
        // 값 검증
        // 중복 검사
        // DB 저장
        // 결과 생성
    }
}
```

이걸 단순히 메서드로만 쪼개는 게 아니라 변경 이유가 다른 책임을 객체로 분리한다
```
AssetExcelFileHandler
AssetExcelHeaderReader
AssetSheetParser
AssetExcelRowValidator
AssetExcelDuplicateChecker
AssetRepository
```

결과적으로 아래와 같이 리팩터링 한다
```java
@Service
@RequiredArgsConstructor
public class AssetExcelUploadService {

    private final AssetExcelFileHandler fileHandler;
    private final AssetSheetParserRegistry parserRegistry;
    private final AssetExcelRowValidator validator;
    private final AssetRepository assetRepository;

    @Transactional
    public UploadResult upload(MultipartFile file) {
        var workbook = fileHandler.read(file);
        var assets = parserRegistry.parse(workbook);

        validator.validate(assets);
        assetRepository.saveAll(assets);

        return UploadResult.success(assets.size());
    }
}
```

## 4. DI의 핵심은 new를 없애는 게 아니다

다음 코드 자체가 나쁜건 아니다
```java
var validator = new AssetExcelRowValidator();
```

문제는 상위 객체가 다음을 모두 결정한다는 것이다 <br/>
아래 코드는 `AssetUploadService`가 객체 사용뿐 아니라 구현 선택과 생성까지 책임지고 있다
```java
public class AssetUploadService {

    private final AssetExcelRowValidator validator
        = new AssetExcelRowValidator();
}
```

DI를 사용하면 결정권을 외부로 넘긴다
```java
@Service
@RequiredArgsConstructor
public class AssetUploadService {

    private final AssetRowValidator validator;
}
```
```java
@Component
public class DefaultAssetRowValidator implements AssetRowValidator {
}
```

- `new` : 내가 사용할 구현체를 내가 결정한다
- DI : 사용할 구현체를 외부 구성에 맡긴다
