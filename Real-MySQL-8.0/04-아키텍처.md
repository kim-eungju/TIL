## 1. MySQL 전체 구조 

가장 중요하다.
```
Client(Spring)
	↓
Connector(JDBC)
	↓
----MySQL Server----
MySQL Engine
- SQL Parser
- Optimizer
- Executor
Storage Engine
- InnoDB
- MyISAM
--------------------
```

### MySQL Engine
SQL을 처리한다.
- SQL Parsing
- 권한 확인
- Optimizer
- 실행 계획 생성

예)
```sql
SELECT * FROM user WHERE id = 1;
```
```
	↓
SQL 문법 검사
	↓
실행 계획 생성
	↓
Storage Engine에게 요청
```

### Storage Engine

실제 데이터를 읽고 저장한다.

대표적으로

InnoDB (거의 99%)
MyISAM(거의 안씀)

거의 InnoDB만 사용한다고 보면 된다.

---

## 2. InnoDB 

현재 MySQL의 기본 Storage Engine

장점
- Transaction 지원
- Row Lock
- MVCC
- Crash Recovery
- Foreign Key

즉,
DB에서 사용하는 기능은 거의 다 InnoDB 덕분이다.

---

## 3. MySQL Thread 구조 

MySQL은 요청마다 Thread가 하나 생성된다.
```
Client1
	↓
Thread1

Client2
	↓
Thread2

Client3
	↓
Thread3
```
Thread가 하는 일
- SQL 실행
- 결과 반환
- Storage Engine 호출

Spring에서
```
Tomcat Thread
	↓
JDBC
	↓
MySQL Thread
```
라고 이해하면 된다.

## 4. Handler API 

MySQL Engine과 Storage Engine이 통신하는 인터페이스
```
MySQL Engine
	↓
Handler API
	↓
InnoDB
```
Engine은
"데이터 읽어"
라고만 요청한다.
실제로 읽는 건 InnoDB.

## 5. 메모리 구조 

매우 중요 
메모리는 크게 
```
Global Memory
Session Memory
```

### Global Memory

모든 Thread가 공유
```
Buffer Pool
Adaptive Hash
Redo Log Buffer
```
대표적으로
__InnoDB Buffer Pool__
가장 중요하다.

### Session Memory
Thread마다 생성
```
Sort Buffer
Join Buffer
Read Buffer
```
Thread 종료되면 사라진다.

## 6. InnoDB Buffer Pool

디스크 대신 메모리에 데이터를 캐싱한다.
```
SQL 실행
    ↓
Buffer Pool에 데이터가 있는가?
    ↓
   없음 | 있음 → Buffer Pool(메모리)에서 바로 읽음 ✅
    ↓
디스크에서 데이터 읽음
    ↓
Buffer Pool에 저장
    ↓
SQL 결과 반환
    ↓
다음 SELECT
    ↓
Buffer Pool에서 바로 읽음 (디스크 접근 없음)
```
메모리에서 바로 읽음
엄청 빠르다.

언제 Buffer Pool에 올라가나?
가장 기본적인 기준은 "읽거나(Read), 수정한(Write) 데이터"이다.

그럼 메모리가 꽉 차면?
여기서 LRU(Least Recently Used) 계열 알고리즘이 동작한다.

```
Buffer Pool

[자주 사용] [사용] [가끔] [오래 안 씀]
                              ↓
                     오래 안 쓴 페이지 제거
```

### Dirty Page

Buffer Pool에서 수정됐지만
아직 디스크에 저장 안 된 페이지
```
Update
	↓
Buffer Pool 수정
	↓
Dirty Page
	↓
나중에 Disk 저장
```

---

## 7. Flush

Dirty Page를 Disk에 저장하는 작업
```
Dirty Page
	↓
Flush
	↓
Disk
```
너무 자주 Flush하면 느려진다.

COMMIT 하면 Flush 하나?
이 부분을 많이 헷갈린다.

COMMIT ≠ Dirty Page Flush
COMMIT 시 반드시 기록되는 것은 Redo Log이다.

---

## 8. Redo Log 

매우 중요
Buffer Pool은 메모리다.
서버가 죽으면?

__"메모리 데이터 사라짐"__

그래서 변경사항을 먼저 Redo Log에 기록한다.
```
UPDATE
	↓
Redo Log 기록
	↓
Buffer Pool 수정
	↓
나중에 Disk 저장
```
```
Crash 발생
	↓
Redo Log로 복구
```

---

## 9. Undo Log 

Transaction Rollback용
```
UPDATE
	↓
기존 데이터 Undo 저장
	↓
새 데이터 기록
```
```
Rollback
	↓
Undo Log 이용
	↓
복구
```

또 하나
__MVCC__ 에서도 사용된다.

Undo Log는 데이터를 변경하는 순간(UPDATE/DELETE/INSERT) 저장된다.
```
트랜잭션 시작
        │
        ▼
UPDATE 실행
        │
        ├── 기존 값("Lee") → Undo Log 저장
        │
        ├── Buffer Pool에서 "Kim"으로 수정
        │
        └── Redo Log 기록
        │
        ▼
COMMIT
```

삭제는?
Undo Log는 즉시 삭제되지 않는다.

왜냐하면
다른 트랜잭션이 아직 이전 버전(Lee)을 보고 있을 수도 있기 때문이다. (__MVCC__)

모든 트랜잭션이 더 이상 필요하지 않게 되면 삭제 된다.
```
Purge Thread
      ↓
Undo Log 삭제
```

---

## 10. Double Write Buffer 

디스크 저장 중
OS 장애가 발생하면
페이지 일부만 저장될 수 있다.
이를 Partial Write라고 한다.
Double Write Buffer는
```
한 번 안전한 공간 저장
	↓
실제 위치 저장
```
으로 데이터 손상을 막는다.

---

## 11. Checkpoint 

Redo Log를
어디까지 Disk에 반영했는지 표시
```
Redo Log
	↓
Checkpoint
	↓
여기까지 저장 완료
```
복구 시간이 줄어든다.

---

## 12. Adaptive Hash Index 

InnoDB가
자주 조회되는 데이터를
자동으로 Hash Index 생성
```
SELECT 반복
	↓
Adaptive Hash 생성
	↓
더 빠르게 조회
```
자동으로 관리된다.

---

## 13. Change Buffer 

Index 수정은 느리다.
그래서
즉시 Index 변경하지 않고
잠시 모아둔다.
```
INSERT
	↓
Change Buffer
	↓
나중에 Index 반영
```
쓰기 성능 향상
