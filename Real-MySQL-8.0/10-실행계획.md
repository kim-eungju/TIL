## 1. 실행계획(Execution Plan) 

가장 중요한 개념

실행계획이란
옵티마이저가 SQL을 어떻게 실행할지 결정한 계획

확인 방법
```sql
EXPLAIN
SELECT *
FROM user
WHERE id = 1;
```
실무에서 SQL이 느리면 가장 먼저 __EXPLAIN__을 확인한다.

---

## 2. SQL 실행 흐름 
```
SQL 작성
	↓
Parser
	↓
Optimizer
	↓
Execution Plan 생성
	↓
Storage Engine(InnoDB)
	↓
결과 반환
```
즉,
실행계획은
옵티마이저의 최종 결과물이다.

---

## 3. EXPLAIN 컬럼

가장 많이 보는 컬럼은 6개뿐이다.
```
id
select_type
table
type
key
Extra
```
이 6개만 알아도 실무에서 충분하다.

---

## 4. type 

가장 중요하다.
Access Type이라고도 한다.

const
```sql
WHERE id = 1
```
- PK 조회
- 가장 빠르다.

eq_ref
- `JOIN`에서 PK로 찾는 경우 매우 좋다

ref
- 보조 인덱스 사용
- 좋은 편

range
- 가장 많이 보는 형태
```sql
WHERE age > 20
```

Index Range Scan
- 좋은 실행계획

index
- 인덱스 전체 읽기
- 조금 아쉽다

ALL
- 최악
- Full Table Scan
- 가능하면 피해야 한다

## 5. key 

사용한 인덱스

예)
```
PRIMARY
```
또는
```

```
`NULL`이면
인덱스 사용 안 함

## 6. possible_keys 

사용 가능한 인덱스
실제로 사용한 것은 key


예)
```

idx_name

	↓
```

---

## 7. rows 

예상 조회 건수

예)
```
rows = 100000
```
느릴 가능성
```
rows = 1
```
좋다.

rows가 적을수록
좋은 실행계획

---

## 8. filtered 

조건을 통과하는 비율

예)
```
100%
	↓
대부분 사용
```
```
10%
	↓
많이 걸러짐
```

---

## 9. Extra 

Using index
- Covering Index
- 가장 좋다.
- 테이블 접근 안 함

Using where
- 조건 필터링
- 일반적이다.

Using temporary
- 임시 테이블 생성
- 좋지 않다.
- 대부분 `GROUP BY`, `ORDER BY`

Using filesort
- 디스크 정렬
- 느리다.
- `ORDER BY` 인덱스를 고려해야 한다.

---

## 10. Using index

예)
```sql
SELECT name
FROM user
WHERE name='Kim'
```
```
name 인덱스만 있으면
	↓
Covering Index
	↓
매우 빠름
```

---

## 11. Using filesort
```sql
ORDER BY created_at
```
```
인덱스 없으면
	↓
Filesort
	↓
느림
```

---

## 12. Using temporary
```sql

```

```
	↓

	↓
메모리
	↓
디스크
	↓
느림
```

## 13. 실행계획이 좋다고 무조건 빠른 것은 아니다 

예)
```
rows=1
```
하지만
```
수백만 번 반복
	↓
느릴 수 있다.
```
실행계획은 예상일 뿐이다.
