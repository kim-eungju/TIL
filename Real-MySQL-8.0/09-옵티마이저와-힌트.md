## 1. 옵티마이저(Optimizer)

가장 중요한 개념
옵티마이저는
가장 효율적인 SQL 실행 방법(실행 계획)을 선택하는 엔진

예)
```sql
SELECT *
FROM user
WHERE id = 100;
```
옵티마이저는
PK 사용할지
보조 인덱스 사용할지
Full Table Scan 할지
비용(Cost)을 계산한 뒤
가장 저렴한 방법을 선택한다.

---

## 2. SQL 실행 과정 
```
SQL 입력
	↓
Parser
	↓
Optimizer
	↓
Execution Plan 생성
	↓
Storage Engine(InnoDB)
	↓
결과 반환
```
즉
옵티마이저가 실행계획을 만든다.

---

## 3. Cost Based Optimizer(CBO) 

MySQL 8.0은
비용 기반 옵티마이저(CBO)
를 사용한다.

예)
옵션 1
```
PK 조회
비용 = 10
```
옵션 2
```
Table Scan
비용 = 5000
```

PK 선택

---

## 4. 통계 정보(Statistics) 

옵티마이저는
통계 정보를 보고 판단한다.

예)
- 테이블 크기
- 인덱스 분포
- Cardinality
- 데이터 개수

통계가 오래되면
잘못된 실행 계획이 나올 수 있다.

---

## 5. Cardinality

08장에서도 나왔던 개념
값의 다양성

예)
성별
```
M
F
```
Cardinality 낮음
	↓
인덱스 효과 작음
```
회원번호
```
Cardinality 높음
	↓
좋은 인덱스
	↓
옵티마이저도 선호

---

## 6. Full Table Scan을 선택하는 이유

많은 사람들이
"인덱스 있는데 왜 안 쓰지?"
라고 생각한다.
대표 이유

### 데이터 대부분 조회
```sql
WHERE age > 1
```
거의 전부 조회, Table Scan이 더 빠름

### Cardinality 낮음
```
gender='M'
```
50%.. 인덱스 의미 없음

### 함수 사용

`YEAR(created_at)`
인덱스 못 탐

---

## 7. Index Merge 

여러 인덱스를 동시에 사용

예)
```
WHERE age=20
OR gender='M'
	↓
age 인덱스 + gender 인덱스
	↓
  Merge
```
---

## 8. Condition Pushdown

조건을
Storage Engine까지
내려보낸다.
```
MySQL Engine
	↓
InnoDB
	↓
조건 필터링
```
불필요한 데이터 전송 감소

---

## 9. ICP(Index Condition Pushdown) 

Index를 읽는 중간에
조건을 검사

예)
```sql
WHERE name='Kim'
AND age>20
```
인덱스를 읽으면서
```
조건 확인
	↓
테이블 접근 감소
```

---

## 10. MRR(Multi Range Read) 

보조 인덱스는
PK를 다시 찾아야 한다.

```
MRR은
PK 조회를
모아서 처리
	↓
랜덤 I/O 감소
```

---

## 11. BKA(Batched Key Access) 

Join 최적화
```
PK 조회를
한 번에 처리
	↓
Join 빨라짐
```

---

## 12. 힌트(Hint) 

옵티마이저에게
"이렇게 해"
라고 알려주는 기능

예)
```sql
SELECT /*+ INDEX(user idx_name) */
```
```
	↓
idx_name 사용 권장

하지만.. 가능하면
안 쓰는 게 좋다.
```

---

## 13. Index Hint 

```sql
USE INDEX(idx_name)
```
사용 추천
```sql
FORCE INDEX(idx_name)
```
강제로 사용
```sql
IGNORE INDEX(idx_name)
```
사용 금지

실무에서는
FORCE INDEX는
정말 마지막 수단

---

## 14. Optimizer Hint 

8.0부터
```sql
/*+ INDEX() */
```
방식 사용

기존 Hint보다
더 권장

---

## 15. 힌트를 남발하면 안 되는 이유 

데이터 분포는 시간이 지나며 바뀐다.

오늘은 PK가 빠르지만
내일은 다를 수도 있다.

옵티마이저는 그때그때 
최적의 실행 계획을 계산한다.

따라서 힌트는 정말 필요한 경우만 사용한다.

---

## 16. 옵티마이저가 틀릴 수도 있다 

대표 원인

오래된 통계 정보
데이터 분포 변경
매우 복잡한 JOIN
비정상적인 Cardinality

이때

실행 계획(EXPLAIN)을
확인해야 한다.
