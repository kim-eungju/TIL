## 1. CHAR vs VARCHAR 

실무에서는 대부분 VARCHAR를 사용한다.

### CHAR
- 고정 길이
- 남는 공간도 모두 저장
```sql
CHAR(10)
'ABC'
```
실제로는 10바이트를 모두 사용
```sql
ABC_______
```

### VARCHAR

- 가변 길이
```sql
VARCHAR(10)
'ABC'
```
실제로는 3글자만 저장(+길이정보)
```sql
ABC
```


언제 CHAR? 거의 없다.

예외
- 국가코드(KR)
- 성별(M/F)
- UUID 일부
- 항상 길이가 동일한 값

그 외에는 전부 `VARCHAR`

## 2. CHARSET(문자셋)

문자 하나가 몇 바이트인지 결정한다.

대표적으로
```sql
latin1 // 1byte
utf8mb3 // 최대 3byte
utf8mb4 // 최대 4byte
```

현재는
`utf8mb4` 사용이 정답
이모지 😀 까지 저장 가능하다.

utf8은 저장 못하는 경우가 있지만
`utf8mb4`는 가능.

## 3. Collation(정렬 방식)

같은 문자열이라도 비교 결과가 달라진다.

예)
```
abc
ABC
```
Case Insensitive
```
utf8mb4_general_ci
abc == ABC
```
Case Sensitive
```
utf8mb4_bin
abc != ABC
```

실무에서는
`utf8mb4_0900_ai_ci` Collation을 가장 많이 사용한다.

| 항목       | utf8mb4_general_ci | utf8mb4_0900_ai_ci |
| -------- | ------------------ | ------------------ |
| MySQL 버전 | 예전부터 사용            | MySQL 8.0 기본       |
| 비교 알고리즘  | 단순 비교              | Unicode 9.0 규칙     |
| 정렬 정확도   | 보통                 | 매우 높음              |
| 다국어 지원   | 좋음                 | 더 좋음               |
| 성능       | 약간 빠름              | 거의 차이 없음           |

## 4. INT / BIGINT 선택

`INT` 범위 약 21억

회원 수, 주문번호, 로그
등이 많아지면 금방 넘는다.

그래서 PK는 `BIGINT` 추천.

JPA에서도
`Long id`
많이 쓰는 이유다.

## 5. FLOAT, DOUBLE 대신 DECIMAL

금액 계산은 절대
```sql
FLOAT
DOUBLE
```
쓰면 안 된다.

왜?
```
0.1
+
0.2
=
0.30000000004
```
오차 발생.


```sql
DECIMAL(10,2)
```
금액은 `DECIMAL` 사용.


```
99999999.99
```
정확하게 저장된다.

## 6. DATETIME vs TIMESTAMP

### DATETIME
- 입력한 날짜 그대로 저장
- TimeZone 영향 거의 없음
- 범위도 매우 넓다.
```
1000년
~
9999년
```

### TIMESTAMP
UTC 기준 저장

조회 시
```
한국
↓
한국시간
```
```
미국
↓
미국시간
```
자동 변환된다.

범위도 작다.
```
1970
~
2038
```
실무

예약일, 생일
`DATETIME`

로그인시간, 시스템로그
`TIMESTAMP`

## 7. AUTO_INCREMENT

```sql

```

```

```

## 8. ENUM

예)
```
ACTIVE
DELETE
WAIT
```
가능.

장점
- 저장공간 적음
- 오타 방지

단점
- 값 추가하려면 `ALTER TABLE` 해야 한다.

그래서 변경 가능성이 있는 값은 ENUM보다 코드 테이블을 사용하는 경우도 많다.

## 9. TEXT / BLOB

TEXT
- 긴 문자열
BLOB
- 바이너리
예)
```
사진
PDF
파일
```
주의 `TEXT`는 `LIKE` 검색이나 정렬에 불리하며,
큰 데이터를 자주 조회하면 성능에 영향을 줄 수 있다.

## 10. JSON

MySQL 8부터 많이 사용하는 타입.
```sql
{
  "name":"kim",
  "age":30
}
```
처럼 저장 가능.

장점
- 스키마 변경이 적다.
- JSON 함수로 내부 값 조회 가능.

단점
- 일반 컬럼보다 검색 성능이 떨어질 수 있다.
- 자주 검색하는 값은 별도 컬럼으로 분리하는 것이 좋다.
