## 1. 트랜잭션(Transaction) 

가장 중요한 개념.
트랜잭션이란 여러 SQL을 하나의 작업 단위로 묶는 것
예시
```sql
UPDATE account SET money = money - 10000 WHERE id = 1;
```
```sql
UPDATE account SET money = money + 10000 WHERE id = 2;
```
```
둘 중 하나라도 실패하면?
	↓
둘 다 취소(Rollback)
	↓
데이터 일관성 유지
```
Spring에서는
```java
@Transactional
public void transfer() {

}
```
이 한 줄이 바로 트랜잭션이다.

---

## 2. ACID 

트랜잭션의 4대 특징

### Atomicity (원자성)

모두 성공
또는
모두 실패
```
O O O
또는
X X X
```

### Consistency (일관성)

트랜잭션 전후
DB 상태가 항상 정상이어야 한다.
예) 잔액 합계는 항상 같다.

### Isolation (격리성)

동시에 실행되는 트랜잭션끼리
서로 영향을 최소화
이 부분이 Lock과 연결된다.

### Durability (지속성)

Commit 완료되면
서버가 죽어도
Redo Log 덕분에 복구된다.

## 3. Commit / Rollback 

```
BEGIN
↓
SQL 실행
↓
Commit
↓
영구 저장
```
Rollback
모든 변경 취소
Spring에서는
Exception 발생 시 자동 Rollback

## 4. Lock(잠금) 

여러 사용자가
동시에 같은 데이터를 수정하면
문제가 발생한다.
그래서 Lock이 필요하다.

예) 
A 와
```sql
UPDATE user
SET name='Kim'
WHERE id=1;
```
동시에 B
```sql
UPDATE user
SET name='Lee'
WHERE id=1;
```

Lock이 없다면
누가 마지막에 저장했는지 모른다.

## 5. Shared Lock / Exclusive Lock 

### Shared Lock (S Lock)

읽기 가능
쓰기 불가

```sql
SELECT ...
LOCK IN SHARE MODE
Exclusive Lock (X Lock)
```

읽기 가능
다른 수정 불가
```
UPDATE
DELETE
INSERT
```
대부분 UPDATE가
Exclusive Lock을 건다.

## 11. MVCC 

Multi Version Concurrency Control
가장 많이 나오는 면접 질문
읽는 사람과
수정하는 사람이
서로 안 기다리도록 만든다.

예) 
```
A
UPDATE
아직 Commit 안 함
↓
B
SELECT
↓
기존 데이터 읽음
↓
대기 안 함
```
Undo Log 덕분이다.

---

## 12. Undo Log 

MVCC의 핵심
```
Old Data
	↓
Undo 저장
	↓
Update
```
`SELECT`는
Undo 데이터를 읽는다.

InnoDB에서는 `INSERT`, `UPDATE`, `DELETE` 모두 Undo Log를 생성하지만, 
저장하는 내용과 목적은 각각 다르다.

- `UPDATE` : 예전 값을 저장한다.
- `DELETE` : 삭제된 행을 저장한다.
- `INSERT` : 새로 만든 행이라는 사실을 기록한다. Rollback 시 삭제하면 된다.

## 19. SELECT LOCK

InnoDB에서 일반적인 SELECT는 락을 걸지 않는다.
대신 MVCC(Multi-Version Concurrency Control)를 이용해 Undo Log에 저장된 이전 버전의 데이터를 읽기 때문이다.

예시 1
- 트랜잭션 A
```sql
UPDATE member
SET name = 'Kim'
WHERE id = 1;
```
- 아직 COMMIT 안 함
- 트랜잭션 B
```sql
SELECT * FROM member WHERE id = 1;
```
이때 트랜잭션 B는 A가 수정 중인 행을 기다리지 않는다.
- 현재 수정 중인 데이터가 아니라
- Undo Log에 있는 이전 버전의 데이터를 읽는다(MVCC)
- 따라서 락 대기 없이 조회가 가능하다.

예시 2 ⭐ (실무에서 서브쿼리 데드락 경험 있음)
```sql
UPDATE member
SET point = (
    SELECT AVG(point)
    FROM member
);
```
여기서
```sql
SELECT AVG(point)
FROM member
```
를 수행하는 읽기(Read) 단계에서는 __트랜잭션 격리 수준__ 에 따라 락의 범위가 다르다. 

| 격리수준 | 서브쿼리 읽기 락 | 락 종류 | 일반 SELECT |
|---|---:|---|---|
| READ UNCOMMITTED | ❌ | 비잠금 읽기 | ❌ 비잠금 (dirty read) |
| READ COMMITTED | ❌ | consistent read | ❌ 비잠금 (consistent read) |
| REPEATABLE READ | ✅ | S next-key lock | ❌ 비잠금 (consistent read) |
| SERIALIZABLE | ✅ | S next-key lock | ✅ S next-key lock |

예시 3
```sql
SELECT * FROM member WHERE id = 1 FOR UPDATE;
```
일반 SELECT는 락이 없지만, 아래와 같은 잠금 읽기(Locking Read)는 락을 건다.
```sql
SELECT * FROM member WHERE id = 1 LOCK IN SHARE MODE;
```
> MySQL 8.0에서는 FOR SHARE 사용 권장

InnoDB에서는 일반 `SELECT`는 MVCC를 이용해 Undo Log의 이전 버전을 읽기 때문에 보통 락을 걸지 않는다. FOR UPDATE나 FOR SHARE 같은 잠금 읽기를 사용할 때만 락을 획득한다.
