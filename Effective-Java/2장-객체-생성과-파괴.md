## Item 1. 생성자 대신 정적 팩터리 메서드를 고려하라

### 정적 팩터리 메서드란?

보통 객체
```java
User user = new User("ejkim");
```
정적 팩터리 메서드
```java
public class User {

    private String name;

    private User(String name) {
        this.name = name;
    }

    public static User create(String name) {
        return new User(name);
    }
}
```
```java
User user = User.create("ejkim");
```
클래스 내부의 static 메서드가 객체를 생성해서 반환하는 방식

JDK 대표 사례
```java
List<String> list = List.of("A");
```

### 장점 
생성자는 이름이 없음
```java
new User("ejkim")
```
반면
```java
User.create("ejkim")
```
의도가 명확함

### 단점
- 생성자를 `private`으로 막는 경우 상속이 불가능 하다.
- 이름을 알아야 사용할 수 있다.

### DTO, Entity, VO 예제

DTO
```java
UserResponse.from(user)
```
Entity
```java
User.create(name, age)
```
VO
```java
Money.of(1000)
Email.of("test@test.com")
```

정리하자면, 

Spring 실무에서 Item 1의 가장 큰 가치는 "생성자에 이름을 붙일 수 있다"이다.

나머지 장점들(구현체 은닉, 캐싱)은 라이브러리/JDK 설계에서 빛나는 장점이고,

구현체를 숨기고 반환 타입을 유연하게 바꿀수 있는 장점 또한
인터페이스 + DI가 이미 같은 문제를 해결하므로
체감도는 낮다.

> __"생성자에 이름을 붙일 수 있다"__ 정도만 기억하자

## Item 2. 생성자 매개변수가 많다면 Builder를 고려하라

일반적인 클래스

```java
public class User {

    private final String name;
    private final int age;
    private final String email;
    private final String phone;
    private final boolean admin;

    public User(
            String name,
            int age,
            String email,
            String phone,
            boolean admin
    ) {
        this.name = name;
        this.age = age;
        this.email = email;
        this.phone = phone;
        this.admin = admin;
    }
}
```
```java
User user = new User(
        "kim",
        30,
        "kim@test.com",
        "010-1111-2222",
        true
);
```
마지막 `false` 가 뭐였지? 이런 상황 나옴
그렇다고 `setter` 를 사용하면 캡슐화에 위배됨

Builder 패턴
```java
@Builder
@Getter
public class User {

    private final String name;
    private final int age;
}
```
```java
User.builder()
    .name("kim")
    .age(30)
    .build();
```
`record` + Builder 패턴도 사용 가능
```java
@Builder
public record User(
    String name,
    int age,
    String email,
    String phone,
    boolean admin
) {}
```

> 매개변수가 많으면 Builder 를 고려하자 
그렇다고, 모든 클래스에 Builder 를 붙이는것은 아님

## Item 3. private 생성자나 enum으로 Singleton임을 보증하라

싱글턴이란?
객체가 하나만 존재
```java
UserService service = UserService.getInstance();
```
Java 로만 구현
```java
public class ConfigManager {

    private static final ConfigManager INSTANCE =
            new ConfigManager();

    private ConfigManager() {}

    public static ConfigManager getInstance() {
        return INSTANCE;
    }
}
```

Spring에서는 직접 싱글턴을 만들지 말고 `Bean`으로 관리
```java
@Service
public class UserService {
   // 여기 필드는 모두 Singleton
}
```


위험한 예제 - 사용자A 와 사용자B 가 동시에 접근 가능
```java
@Service
public class LoginService {

    private String loginUserId;

    public void login(String userId) {
        this.loginUserId = userId;
    }

    public String getLoginUserId() {
        return loginUserId;
    }
}
```


올바른 예제
```java
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;
    private final ObjectMapper objectMapper;
}
```

그러나, `list`는 안전하지 않다. 
언제든지 값이 바뀔 수 있음
```java
@Service
@RequiredArgsConstructor
public class UserService {

    private final List<String> users = new ArrayList<>();
}
```

```java
users.add("kim");
users.remove("kim");
users.clear();
```

어쩔수 없이 써야한다면?
`ConcurrentHashMap` 을 사용하자 (안전하면서 빠름)
```java
private final ConcurrentHashMap<String, User> cache
        = new ConcurrentHashMap<>();
```

서로 다른 bucket이라면 동시에 처리 가능
```java
map.put("A", "1");
```

```java
map.put("Z", "2");
```
`ConcurrentHashMap`은 전체 `Map`을 잠그지 않고 세분화된 락을 사용한다.

> 인스턴스가 하나만 존재해야 하는 클래스는 `private` 생성자 또는 `enum`을 사용해 싱글턴임을 확실히 보장하라

## Item 5. 자원을 직접 명시하지 말고 의존 객체 주입을 사용하라

아래 처럼 `UserService`가 `UserRepository`를 직접 생성하면 안된다.

```java
public class UserService {

    private final UserRepository userRepository =
            new UserRepository();

    public User findById(Long id) {
        return userRepository.findById(id);
    }
}
```

Spring에서는 알아서 `UserRepository`를 만들고, `UserService(userRepository)` 주입해준다. 
```java
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;
}
```

> `UserService`가 `UserRepository`를 직접 생성하면 사용과 생성 두 책임을 동시에 갖게 되어 결합도가 높아진다. 그래서 외부(Spring)가 생성해서 주입해주는 게 더 좋다. (__DI & IoC__)

## Item 6. 불필요한 객체 생성을 피하라

요청 올 때마다 `Mapper`를 생성
```java
@Service
public class UserService {

    public void save() {
        UserMapper userMapper = new UserMapper();
        ...
    }
}
```

Spring이 생성한 객체를 계속 재사용
```java
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserMapper userMapper;
}
```
> 같은 객체를 계속 새로 만들지 말고 재사용할 수 있으면 재사용하자. 즉, 매번 `new` 하지 말고, 스프링이 관리하는 `Bean`을 재사용하라.

## Item 7. 다 쓴 객체 참조를 해제하라

Java는 GC가 있어서 메모리 관리를 직접 하지 않아도 되지만, __참조(reference)__를 잘못 관리하면 GC도 어쩔 수 없다.

잘못된 코드 예제
```java
public class Stack {
    private Object[] elements;
    private int size = 0;

    public Stack(int capacity) {
        elements = new Object[capacity];
    }

    public void push(Object e) {
        elements[size++] = e;
    }

    public Object pop() {
        if (size == 0)
            throw new EmptyStackException();

        return elements[--size];
    }
}
```
`null`을 넣으면 참조하는 객체가 없는것으로 판단하여 회수할 수 있다.
```java
public Object pop() {
    if (size == 0)
        throw new EmptyStackException();

    Object result = elements[--size];
    elements[size] = null;    // 참조 제거
    return result;
}
```

> 위 예제는 배열로 직접 자료구조를 구현했지만, 실무에서는 대부분 `List`를 사용한다. `List`는 내부적으로 `null`을 넣어 참조를 끊는다.

## Item 9. try-finally보다는 try-with-resources를 사용하라


`try-finally`는 `close()`를 직접 호출해야 한다.
```java
FileInputStream fis = new FileInputStream("test.txt");

try {
    // 파일 읽기
} finally {
    fis.close();
}
```
예를 들어 두 개를 사용한다면?
중첩된 `try-finally`가 계속 생긴다. 코드가 훨씬 복잡해짐
```
FileInputStream fis
BufferedReader br
```
```java
FileInputStream fis = new FileInputStream("a.txt");

try {
    BufferedReader br =
        new BufferedReader(new InputStreamReader(fis));

    try {
        // 읽기
    } finally {
        br.close();
    }

} finally {
    fis.close();
}
```

그래서 `try-with-resources`를 사용한다.
`try-with-resources`는 블록이 끝나면 JVM이 자동으로 `close()` 호출해 준다.

```java
/*
try (자원 생성) {
    // 자원을 사용하는 코드
}
*/
try (
	FileInputStream fis = 
    	new FileInputStream("test.txt")
) {
    int data = fis.read();
    System.out.println(data);
}
```
> `try-with-resources`는 `AutoCloseable`객체의 `close()`를 컴파일러가 자동으로 호출해 주는 문법이다. 따라서 개발자가 `finally`에서 직접 `close()`를 작성할 필요가 없다.
