## Item 42. 익명 클래스보다는 람다를 사용하라

```java
List<String> list = List.of("banana", "apple", "orange");
```
Java 8 이전
```java
Collections.sort(list, new Comparator<String>() {
    @Override
    public int compare(String a, String b) {
        return a.compareTo(b);
    }
});
```
Java 8 이후
```java
Collections.sort(list, (a, b) -> a.compareTo(b));
```
또는
```java
list.sort((a, b) -> a.compareTo(b));
```
> 함수형 인터페이스(추상 메서드가 하나인 인터페이스)는 익명 클래스보다 람다를 사용하는 것이 더 간결하고 읽기 쉽다. 하지만 `this`를 사용하거나, 객체의 상태를 표현해야 하거나, 추상 메서드가 여러 개인 인터페이스를 구현해야 하는 경우에는 익명 클래스나 일반 클래스를 사용하는 것이 적절하다.

## Item 43. 람다보다는 메서드 참조를 사용하라

람다 예제
```java
list.forEach(s -> System.out.println(s));
```
메서드 참조 예제

```java
list.forEach(System.out::println);
```
Item 42의 예제 또한 아래와같이 바꿀 수 있다
```java
list.sort((a, b) -> a.compareTo(b));
```
```java
list.sort(String::compareTo);
```
실무에 자주 사용되는 예
```java
List<String> names = users.stream()

        .toList();
```

```java
// 기존 메서드를 그대로 호출하지 않는경우 람다를 유지하자
user -> user.getName().toUpperCase()
```

## Item 44. 표준 함수형 인터페이스를 사용하라

우선 `Function`인터페이스가 뭔지 알아보자
```java
@FunctionalInterface
public interface Function<T, R> {

    R apply(T t);
}
```
T를 입력받아서 R을 반환한다

문자열을 받아 문자열 길이를 반환하는 예제
```java
Function<String, Integer> getLength =
        value -> value.length();
```

이걸 메서드로 작성하면?
```java
public int getLength(String value) {
    return value.length();
}
```
차이는 일반 메서드는 클래스에 정의하지만, `Function`은 함수 자체를 변수에 담거나 다른 메서드에 전달할 수 있다

```java
public void printResult(
        String value,
        Function<String, Integer> function
) {
    Integer result = function.apply(value);
    System.out.println(result);
}
```
호출하는 쪽에서 동작을 넘긴다
즉 `printResult()`는 문자열을 어떻게 처리할지 직접 결정하지 않고, 처리 방법을 외부에서 주입받는 구조가됨
```java
printResult("hello", value -> value.length());
```

다시 Item 44 본론으로 돌아와서 아래와 같이 직접 인터페이스를 만들 수 있다.
```java
@FunctionalInterface
public interface StringConverter {
    String convert(String value);
}
```
그러나, Java에 이미 똑같은 인터페이스가 있는데 굳이?
표준 인터페이스를 사용하면 아래와 같은 장점이 있다
- 누구나 의미를 안다
- API가 통일된다
- 메서드 조합이 가능하다

> 람다와 메서드 참조를 사용할 때 굳이 새로운 함수형 인터페이스를 만들지 말고, Java가 제공하는 표준 함수형 인터페이스를 최대한 사용하라

## Item 45. 스트림은 주의해서 사용하라

스트림이란? 아래의 방식을
```java
List<String> names = List.of("kim", "lee", "park");

for (String name : names) {
    System.out.println(name.toUpperCase());
}
```
이런 파이프라인 형태로 처리하는것이 스트림이다.
```java
names.stream()
     .map(String::toUpperCase)
     .forEach(System.out::println);
```
```
생성
 ↓
필터
 ↓
변환
 ↓
정렬
 ↓
출력
```

스트림은 "무엇을 할 것인지"를 표현하고, 반복문은 "어떻게 반복할 것인지"를 표현한다.

```java
List<String> result =
    users.stream()
         .filter(User::isAdult)
         .map(User::getName)
         .sorted()
         .toList();
```
위 코드는 읽기만 해도 의도를 쉽게 파악할 수 있다
```
성인만
→ 이름만 추출
→ 정렬
→ 리스트 생성
```

다시 Item 45로 돌아와서 그럼 왜 주의해서 사용하라고 할까?
```java
users.stream()
     .filter(...)
     .map(...)
     .sorted(...)
     .distinct()
     .limit(10)
     .peek(...)
     .map(...)
     .collect(...)
```
너무 긴 스트림은 오히려 파악이 어렵다.
파악도중 "지금 어디였지?" 하게된다

> 스트림을 사용할 때 스스로 질문해 보자
> - 중간에 `break` 나 `continue`를 사용하지 않는지?
> - 읽기 쉬운가?
> - 반복문보다 짧은가?
> - 중간 상태를 관리할 필요가 없는가?
> - 함수형 스타일이 자연스러운가?

## Item 46. 스트림에서는 부작용 없는 함수를 사용하라

스트림은 원래 아래와 같이 흘러가도록 만들어졌다.
```
입력
 ↓
변환
 ↓
변환
 ↓
결과
```

그런데 아래와 같은 코드는 외부 객체(`result`)를 변경한다 이는 스트림의 철학이 깨진것이다.

```java
List<String> result = new ArrayList<>();

users.stream()
     .map(User::getName)
     .forEach(result::add);
```
```
입력
 ↓
변환
 ↓
외부 List 수정
 ↓
변환
```

나쁜 예
```java
List<String> names = new ArrayList<>();

users.stream()
     .map(User::getName)
     .forEach(names::add);
```
- 외부 리스트를 미리 생성한다.
- 스트림이 외부 리스트를 계속 수정한다.
- 명령형 반복문을 스트림 문법으로 옮긴 형태다.
- 병렬 처리 시 공유 상태 문제가 생길 수 있다.

좋은 예
```java
List<String> names =
    users.stream()
         .map(User::getName)
         .toList();
```
- 스트림이 결과 리스트를 직접 만든다.
- 외부 상태를 변경하지 않는다.
- 코드의 의도가 명확하다.
- 스트림 방식에 더 자연스럽다.

> 
> - 스트림의 람다는 부작용이 없어야 한다.
> - 외부 컬렉션이나 객체를 수정하지 말고 `map`, `filter`, `collect`, `toList()` 같은 연산으로 결과를 만들어라.
> - `forEach`는 계산을 위한 도구가 아니라, 계산이 끝난 결과를 출력하거나 전달하는 등 소비하는 용도로 사용하라.
> 조슈아 블로크가 말하고 싶은 것은
> __"스트림 안에서는 외부 상태를 건드리지 말고, 결과를 반환하는 순수한 함수처럼 작성하라."__ 이다.

## Item 47. 반환 타입으로는 스트림보다 컬렉션이 낫다

`Stream`은 한 번만 사용할 수 있다.
```java
Stream<String> stream = getNames();
stream.forEach(System.out::println);
// 예외 발생
stream.count();
```
`Collection`은 여러번 사용할 수 있다.
```java
List<String> list = getNames();
list.forEach(System.out::println);
System.out.println(list.size());
System.out.println(list.contains("Kim"));
```

## Item 48. 스트림 병렬화는 주의해서 적용하라

병렬 스트림이란?
```java
list.stream()
    .map(...)
    .filter(...)
    .collect(...)
```
일반 스트림은 순서대로 하나씩 처리한다
```
CPU1

1
2
3
4
5
6
```
반면 병렬 스트림은 여러 CPU코어가 동시에 작업한다
```java
list.parallelStream()
```
```
CPU1 : 1 2
CPU2 : 3 4
CPU3 : 5
CPU4 : 6
```
그렇다고 항상 빠른건 아니다 100개의 데이터를 처리한다고 가정해보자
```
데이터 분할
	↓
스레드 생성
	↓
각 스레드 실행
	↓
결과 합치기
```
이 비용이 생각보다 크다

그럼 언제 병렬화가 효과적인가?
- 데이터가 충분히 많을 때 ex) 100만건
- 작업이 무거울 때 ex) 이미지 압축, 복잡한 계산
  - `.map(this::compressImage)`
  - `.map(this::calculateAI)`
- 서로 영향을 주지 않을 때
  - `.map(User::calculateScore)`
  
> 병렬화는 성능 측정을 통해 이득이 확인된 경우에만 적용하자
