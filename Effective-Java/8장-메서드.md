## Item 49. 매개변수가 유효한지 검사하라

매개변수를 검사하지 않으면 오류가 발생한 위치를 찾기가 매우 어렵다.

잘못된 값이 들어오는 순간 바로 예외를 발생시키자
`IllegalArgumentException`발생
```java
public void setAge(int age) {
    if (age < 0) {
        throw new IllegalArgumentException("나이는 0 이상이어야 합니다.");
    }
    this.age = age;
}
```

`Objects.requireNonNull`를 적극 활용하자
```java
public void save(User user) {
    Objects.requireNonNull(user);
}
```
또는 `NullPointerException`
```java
Objects.requireNonNull(user, "user는 null일 수 없습니다.");
```
>
> - 메서드의 입구에서 매개변수를 검증한다.
> - 잘못된 값은 즉시 예외를 던져(Fail Fast) 문제를 빨리 발견한다.
> - `Objects.requireNonNull()`을 적극 활용한다.

## Item 50. 적시에 방어적 복사본을 만들라

문제 발생 예시
`User`는 아무것도 하지않았는데, 외부에서 내부 상태를 바꿔버렸다
```java
List<String> names = new ArrayList<>();
names.add("Kim");

User user = new User(names);

names.add("Lee");
```

Spring에서는 언제 많이 쓰나?
```java
public User(UserRequest request) {
    this.roles = List.copyOf(request.getRoles());
}
```
`DTO` -> `Entity` 변환 (컬렉션을 그대로 저장하지 않는다)

`List.copy()`가 반환하는 것은 불변 리스트다
```java
List<String> list = new ArrayList<>(); // add() 가능
```
```java
List<String> list 
	= List.copyOf(...); 
    // throw UnsupportedOperationException
```

>
> - 가변(Mutable) 객체는 그대로 저장하거나 반환하지 말고 복사해서 사용한다.
> - 생성자에서는 외부에서 받은 객체를 복사하여 내부 상태를 보호한다.
> - `Getter`에서도 내부 객체를 그대로 반환하지 않고 복사본이나 불변 객체를 반환한다.
> - `List.copyOf()`는 복사 + 불변 객체를 만들어주므로 현대 Java에서 가장 권장되는 방법이다.

## Item 51. 메서드 시그니처를 신중히 설계하라

- 메서드 이름은 신중하게 짓기
- 매개변수 개수는 가능한 적게
- 같은 타입 매개변수가 여러 개라면 특히 위험
  - 나쁜 예 
    - `setRange(int start, int end)`
- boolean 매개변수는 피하라
  - 나쁜 예
    - `save(user, true)`
  - 좋은 예 (메서드를 나누자) 
    - `save(user)`
    - `saveForce(user)`
- 오버로딩은 신중하게
  - 매개변수 타입이 명확히 다를 때만 사용하는 것이 좋다
  - 나쁜 예 
    - `remove(int index)`
    - `remove(Object o)`
  
- 매개변수 객체를 활용하라
  - 나쁜 예 
    - `search(ip,
    host,
    group,
    os,
    owner,
    vendor,
    status,
    assetType,
    startDate,
    endDate)`
  - 좋은 예 (DTO나 VO를 고려하자)
    - `search(condition)`

## Item 52. 다중정의는 신중히 사용하라

다중정의(Overloading)란?
```java
void print(String s) {}
void print(int n) {}
void print(double d) {}
```
이건 문제가 없음
매개변수 타입이 명확하게 다르다

그럼 문제가 되는건? 아래 두가지를 기억하자
- 오버로딩은 __컴파일 시점__에 어떤 메서드를 호출할지 결정한다.
- 오버라이딩은 __실행 시점(Runtime)__ 에 결졍된다.

```java
class CollectionClassifier {

    public static String classify(Set<?> s) {
        return "Set";
    }

    public static String classify(List<?> l) {
        return "List";
    }

    public static String classify(Collection<?> c) {
        return "Collection";
    }
}
```
```java
Collection<?>[] collections = {
    new HashSet<String>(),
    new ArrayList<Integer>(),
    new HashMap<String, String>().values()
};

for (Collection<?> c : collections) {
    System.out.println(classify(c));
}
```
예상하는 결과
```java
Set
List
Collection
```
실제 결과
```java
Collection
Collection
Collection
```
변수 타입
```java
Collection<?> c
```

> 매개변수 타입만 다른 오버로딩은 개발자가 예상과 다른 메서드를 호출하게 만들 수 있다.

## Item 53. 가변인수는 신중히 사용하라

적절한 사용 예시
```java
void error(String message, Object... args)
```
```java
log.error("자산 {} 등록 실패", assetId);
log.error("자산 {} 등록 실패. 사용자={}", assetId, userId);
log.error("자산 {} 등록 실패. 사용자={}, IP={}", assetId, userId, ip);
```

그냥 "가변인수로만 받아도 되지않나?"
이건 잘못된 생각이다
```java
public void error(Object... args)
```
왜?
```java
error();                     // 컴파일 성공
error(assetId);              // 컴파일 성공
error("등록 실패");           // 컴파일 성공
```
결국 내부에서 아래와 같은 검사를 해야한다
```java
if (args.length == 0) {
    throw ...
}
```

> 필수값까지 가변인수로 받지말고, 필수값과 가변값을 분리하자

## Item 54. null이 아닌, 빈 컬렉션이나 배열을 반환하라

나쁜 예
```java
public List<User> getUsers() {
    if (users.isEmpty()) {
        return null;
    }

    return users;
}
```

좋은 예
```java
public List<User> getUsers() {
    if (users.isEmpty()) {
        return Collections.emptyList(); // 또는 return List.of();
    }

    return users;
}
```

> 왜 `null`보다 빈 컬렉션이 좋은가?
가장 큰 이유는 호출하는 사람이 편해진다

## Item 55. 옵셔널 반환은 신중히 하라

우선 `Optional`을 잘못 쓰고 있는 예

`List` 자체가 이미 "없음"을 표현할 수 있는데 굳이?
```java
Optional<List<User>>
```
`Optional`을 필드로 쓰는 것도 권장되지 않는다
JPA/Jackson 같은 프레임워크와도 궁합이 좋지 않다.
```java
public class User {
    private Optional<String> nickname;
}
```
메서드 파라미터 `Optional`도 별로다
```java
public void updateUser(
    Long id,
    Optional<String> nickname
)
```
반환값이 없는게 비정상인 경우에도 `Optional`을 안쓰는게 좋다
```java
Optional<User> createUser(...);
Optional<Asset> updateAsset(...);
```

그럼 언제 사용할까? 

⭐ 조회결과가 0개 또는 1개인 메서드의 반환타입과 궁합이 좋다
```java
Optional<User> findUserByEmail(String email);
Optional<Asset> findAssetByIp(String ip);
Optional<Config> findCustomConfig(Long userId);
Optional<LocalDateTime> findLastLoginTime(Long userId);
```

> `Optional`은 단순한 `NPE` 방지 도구라기보다 __값이 없을 수 있다는 사실을 API에 명시하는 도구__에 가깝다.
