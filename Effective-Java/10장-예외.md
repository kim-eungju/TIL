## Item 69. 예외는 진짜 예외 상황에만 사용하라

나쁜 예제 

예외를 정상적인 분기 처리에 사용하고 있다.

또한 `NPE`가 발생했다고 해서 반드시 `user`가 없어서 발생했다고 보장할 수도 없다.
```java
try {
    User user = userMap.get(userId);

    return user.getName();
} catch (NullPointerException e) {
    return "사용자 없음";
}
```
좋은 예제 

정상적인 로직을 더 이상 진행할 수 없는 예외적인 상황을 예외로 표현한다.
```java
User user = userRepository.findById(id)
        .orElseThrow(() -> new UserNotFoundException(id));
```
```java
if (!isValidFile(file)) {
    throw new VADAException(VADAReturnCode.BAD_FILE_UPLOAD);
}
```

> 예외를 정상적인 로직의 흐름 제어 수단으로 사용하지 말고, 진짜 예외적인 상황에만 사용하라.

## Item 70. 복구할 수 있는 상황에는 검사 예외를, 프로그래밍 오류에는 런타임 예외를 사용하라

복구가 가능한 상황에선 `CheckedException`을 고려하자
```java
try {
    primaryServer.send();
} catch (ServerException e) {
    backupServer.send(); // 다른 방법으로 정상 처리
}
```
반면, 

호출자가 `catch`해서 정상 흐름으로 복구할게 아니라면 `RuntimeException`를 사용하면 된다
```java
if (amount < 0) {
    throw new IllegalArgumentException();
}
```

```java
if (balance < amount) {
    throw new InsufficientBalanceException();
}
```

> `Checked Exception`을 아무 생각 없이 만들지 말고, 호출자에게 복구 책임을 강제할 이유가 있을 때만 사용하자

---

## Item 71. 필요 없는 검사 예외 사용은 피하라

`CheckedException`이 이론적으로 맞더라도, 진짜 그걸 강제할 가치가 있는지 다시 생각해보자

API 사용자에게 부담을 주는 설계다
```java
try {
    service.execute();
} catch (SomeException e) {
    ...
}
```
```java
void foo() throws SomeException
```

그렇다고 "무조건 `CheckedException`을 사용하지 말자" 는 아니다

`CheckedException`을 고려할 수 있는 사례
```
송금 시도
   ↓
잔액 부족 CheckedException
   ↓
다른 계좌로 결제할래?
금액을 줄일래?
충전할래?
   ↓
계속 진행 가능
```

Item 70과 Item 71을 요약하자면,
```
         예외 상황 발생
              │
      복구할 수 있는가?
         /          \
       NO            YES
       │              │
RuntimeException      │
                      │
            호출자에게 복구를
            강제할 가치가 있는가?
                /         \
              NO           YES
              │             │
       RuntimeException   Checked
```

> `CheckedException`은 단순히 "복구 가능한 예외"에 사용하는 것이 아니라, 호출자가 그 자리에서 복구 행동을 하도록 강제할 가치가 있을 때 빛난다.

## Item 72. 표준 예외를 사용하라

적절한 표준 예외가 존재한다면 우선 사용하자

__대표적인 표준 예외__

```
잘못된 인자
→ IllegalArgumentException

잘못된 객체 상태
→ IllegalStateException

허용하지 않는 null
→ NullPointerException

잘못된 index
→ IndexOutOfBoundsException

지원하지 않는 기능
→ UnsupportedOperationException
```

__표준 예외__ 

이미 Java에서 제공하는 예외만으로 실패 원인을 충분히 표현할 수 있다면 표준 예외를 사용한다.
```java
public record MacAddress(String value) {

    public MacAddress {
        if (value == null) {
            throw new NullPointerException("value");
        }

        if (!isValid(value)) {
            throw new IllegalArgumentException(
                "Invalid MAC address: " + value
            );
        }
    }
}
```

__커스텀 예외__

"중복 자산"이라는 비즈니스 의미 자체가 중요한 경우 커스텀 예외를 사용할 가치가 있다
```java
if (assetRepository.existsByIp(ip)) {
    throw new AssetAlreadyExistsException(ip);
}
```

> 적절한 표준 예외가 있다면 우선 사용하고, 도메인/비즈니스 의미를 별도로 표현할 가치가 있다면 커스텀 예외를 고려한다.

## Item 73. 추상화 수준에 맞는 예외를 던지라

내부에서 발생한 예외를, 사용하는 사람이 이해하기 쉬운 예외로 바꾸자

__회원조회 예제__

`Controller` 입장에서는 `NoSuchElementException` 을 보면 애매하다
```java
public Member getMember(Long id) {
    try {
        return memberRepository.findById(id);
    } catch (NoSuchElementException e) {
        throw e;
    }
}
```
```
NoSuchElementException
→ 뭐가 없다는 거지?
→ 회원이 없다는 건가?
→ List에서 뭔가 못 찾았나?
```
그래서 `Service`에서 의미 있는 예외(`MemberNotFoundException`)로 바꿔준다
```java
public Member getMember(Long id) {
    try {
        return memberRepository.findById(id);
    } catch (NoSuchElementException e) {
        throw new MemberNotFoundException(id, e);
    }
}
```

__Excel 업로드 예제__

`InvalidFormatException`은 엑셀 라이브러리 내부의 저수준 예외다
```java
public void upload(MultipartFile file) {
    try {
        readExcel(file);
    } catch (InvalidFormatException e) {
        throw e;
    }
}
```
"`Apache POI`의 `InvalidFormatException`이 발생했다" 라고 전달할게 아니라,

"엑셀 파일이 잘못됐다" 라고 전달하는게 맞다

```
InvalidFormatException
        ↓
      번역
        ↓
InvalidExcelFileException
        ↓
Controller
```
`MemberService`라면 회원과 관련된 의미 있는 예외를 던지고, `AssetExcelService`라면 엑셀 업무와 관련된 의미 있는 예외를 던지자

> 결론은 "내부 사정이 담긴 예외를 그대로 위에 던지지 말고, 이 계층에서 무슨 일이 일어났는지 알 수 있는 예외로 바꿔라."
