## Item 78. 공유 중인 가변 데이터는 동기화해 사용하라

여러 스레드가 동시에 데이터를 수정해서 값이 망가지는 것을 막아야한다

Spring의 빈은 기본적으로 싱글턴이므로 하나의 빈 인스턴스를 여러 요청 스레드가 공유한다. 따라서 서비스에 요청별 데이터를 가변 필드로 두지 말고, 매개변수나 지역 변수로 관리하여 __무상태(stateless)__ 로 설계하는 것이 안전하다.

```java
@Service
public class OrderService {

    // 요청마다 달라지는 값을 필드에 저장하면 위험하다.
    private String currentUserId;
}
```

특정 상황에서 공유 가변 상태가 꼭 필요하다면 목적에 맞는 동시성 도구를 사용하자

- 단순 값의 가시성만 필요: `volatile`
- 숫자 증가 등의 단일 원자 연산: `AtomicInteger`
- 상태를 한 번만 변경해야 하는 경우: `AtomicBoolean`
- 여러 스레드가 공유하는 Map: `ConcurrentHashMap`
- 여러 연산을 하나로 묶어 보호해야 하는 경우: `synchronized`, `Lock`

> 가능하면 애초에 가변 데이터를 공유하지 말자

## Item 79. 과도한 동기화는 피하라

아래의 코드는 광범위한 `synchronized` 때문에 { DB조회, 결제 API, DB저장 } 까지 다음 스레드가 전부 기다려야 한다
```java
public synchronized void processOrder(Long orderId) {

    Order order = orderRepository.findById(orderId);

    order.process();

    paymentClient.requestPayment(order);

    orderRepository.save(order);
}
```

가능하다면 동기화가 정말 필요한 부분만 좁히자
```java
public void processOrder(Long orderId) {

    Order order = orderRepository.findById(orderId);

    synchronized (lock) {
        order.process();
    }

    paymentClient.requestPayment(order);

    orderRepository.save(order);
}
```

내가 락을 잡은 채로 내가 통제하지 못하는 코드를 실행시키지 말자
```java
synchronized (lock) {

    // 여기서는 내가 lock을 소유하고 있음

    paymentService.pay(); // 구현 세부사항을 모름
}
```

⭐ 직접 복잡하게 동기화(`synchronized`) 하기보다 `java.util.concurrent`에 있는 고수준 도구를 적극적으로 활용해보자
```
ConcurrentHashMap
AtomicInteger
BlockingQueue
CopyOnWriteArrayList
ExecutorService
```

> synchronized 블록 안에서는 가능한 한 적은 일만 하고, 특히 락을 잡은 상태에서 외부에서 넘어온 코드를 호출하지 말자

## Item 80. 스레드보다는 실행자, 태스크, 스트림을 애용하라

`new Thread()` 를 직접 사용하지 말자
```java
new Thread(() -> doSomething()).start(); // 지양
```

작업(Task)과 실행(Thread)을 분리하자

개발자는 무슨 작업을 할지 작성하고, 어떤 스레드에서 실행할지는 Executor에게 맡긴다.
```java
executor.execute(() -> doSomething());
```

Spring에서는 보통 `@Async`, `TaskExecutor`를 사용한다 (`@Async`는 다른 스레드라는 걸 반드시 기억하자)

```java
@Async
public void sendEmail() {
    // 작업
}
```

`@Async` 사용시 주의할 점
```java
@Transactional
public void createOrder() {
    orderRepository.save(order);

    emailService.sendEmail(); // @Async

    throw new RuntimeException("주문 처리 실패");
}
```

`@Transactional` 안에서 `@Async`를 호출했다고 해서, 비동기 작업도 같은 트랜잭션이라고 생각하면 안 된다.

```
Thread A                         Thread B

@Transactional
주문 저장
   │
   ├──── @Async ───────────────→ 메일 발송
   │
   ↓
예외 발생
   ↓
ROLLBACK

DB: 주문 없음 ❌
메일: 주문 완료 메일 발송됨 ✅
```

> Spring에서는 스레드를 직접 만들지 말고, 작업만 정의해서 @Async나 TaskExecutor 같은 실행자에게 맡겨라.

## Item 81. wait와 notify보다는 동시성 유틸리티를 애용하라

옛날 방식 `wait()`, `notify()` 사용

제대로 구현하는 게 굉장히 어렵다
```java
synchronized (queue) {
    while (queue.isEmpty()) {
        queue.wait();
    }

    String data = queue.remove();
}
```
```java
synchronized (queue) {
    queue.add("hello");
    queue.notifyAll();
}
```

그래서 Java 5 버전 부터 `java.util.concurrent`를 제공한다

| 필요한 기능          | 사용할 것                         |
| --------------- | ----------------------------- |
| 스레드 안전한 Queue   | `BlockingQueue`               |
| 스레드 풀           | `ExecutorService`             |
| 특정 개수의 작업 기다리기  | `CountDownLatch`              |
| 여러 스레드가 서로 기다리기 | `CyclicBarrier`               |
| 동시 접근 개수 제한     | `Semaphore`                   |
| Future 결과 처리    | `Future`, `CompletableFuture` |
| 동시성 Map         | `ConcurrentHashMap`           |

> 스레드 간 협력을 직접 wait/notify로 구현하지 말고, 목적에 맞는 java.util.concurrent의 고수준 도구를 사용하자.

## Item 82. 스레드 안전성 수준을 문서화하라

핵심은 "thread-safe다/아니다" 뿐 아니라, 어느 범위까지 보장하는지 알려주는 것

```java
/**
 * Thread-safe한 캐시.
 *
 * get(), put()은 여러 스레드에서 동시에 호출해도 안전하다.
 * 단, 여러 메서드를 조합한 복합 연산의 원자성은 보장하지 않는다.
 * -> get(), put()은 thread-safe하지만, get() -> 판단 -> put() 같은 복합 작업까지 안전한 건 아니다.
 */
@Component
public class AssetCache {

    private final Map<Long, Asset> cache = new ConcurrentHashMap<>();

    public Asset get(Long id) {
        return cache.get(id);
    }

    public void put(Long id, Asset asset) {
        cache.put(id, asset);
    }
}
```

> 여러 스레드가 공유하는 클래스라면, 동시에 사용할 때 어디까지 안전한지 명확하게 문서화하라.

## Item 83. 지연 초기화는 신중히 사용하라

우선, 왜 초기화를 미루는가?

`OrderService` 가 생성되면 `ReportGenerator` 도 무조건 생성된다

그런데 `ReportGenerator` 생성 비용이 크고, 실제로는 일부 기능에서만 사용한다고 가정하면 아래는 비효율적인 코드다
```java
public class OrderService {

    private final ReportGenerator reportGenerator
        = new ReportGenerator();
}
```

지연 초기화를 적용하면 정말 필요할 때 초기화할 수 있다
```java
public class OrderService {

    private ReportGenerator reportGenerator;

    public ReportGenerator getReportGenerator() {
        if (reportGenerator == null) {
            reportGenerator = new ReportGenerator();
        }

        return reportGenerator;
    }
}
```

Spring 빈으로 바꾸면 이렇게 작성할 수 있다

```java
@Service
public class OrderService {

    private final ReportGenerator reportGenerator;

    public OrderService(@Lazy ReportGenerator reportGenerator) {
        this.reportGenerator = reportGenerator;
    }

    public ReportGenerator getReportGenerator() {
        return reportGenerator;
    }
}
```

장점과 단점

장점
- 무거운 빈의 생성 비용 절약
- 애플리케이션 시작 시간 단축
- 사용하지 않는 빈은 아예 생성하지 않음

단점
- 첫 요청이 느려짐
- 초기화 오류가 실행 중에 늦게 발견됨
- 프록시와 동시성 때문에 코드가 복잡해질 수 있음 (Spring `@Lazy`는 안하게 관리)

> 기본은 즉시 초기화다. 생성 비용이 크고 실제로 사용하지 않을 가능성이 높은 경우에만, 성능 측정 후 @Lazy를 사용하자.
