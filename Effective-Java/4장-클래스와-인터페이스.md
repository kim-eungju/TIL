## item 15. 클래스와 멤버의 접근 권한을 최소화하라

객체가 그냥 데이터 덩어리
```java

    public String name;
    public String platformType;
    public String ip;

```
OOP, 캡슐화, 유지보수성의 핵심 ⭐ 
객체가 자기 상태를 관리
```java
public class Asset {

    private String ip;

    public void changeIp(String ip) {
        validate(ip);
        this.ip = ip;
    }

```
> `public`으로 만들 이유가 없으면 `private`로 만들어라.

## Item 16. public 클래스에서는 public 필드가 아닌 접근자 메서드를 사용하라

객체의 상태를 직접 노출하지말고 `Getter/Setter`를 통해 접근하자

```java
public class User {
    public String name;
    public int age;
}

User user = new User();
user.age = -10; // 누구나 이상한 값을 넣을 수 있음
```
```java
public class User {
    private String name;
    private int age;

    public int getAge() {
        return age;
    }

    public void setAge(int age) {
        if (age < 0) {
            throw new IllegalArgumentException();
        }
        this.age = age;
    }
}
```
> 필드는 `private`으로 숨기고, 필요한 경우에만 접근자 메서드를 제공한다. `Setter`는 무분별하게 만들지 말고, 필요한 경우 직접 구현하여 상태 변경을 제어한다.

## Item 17. 변경 가능성을 최소화하라

가능하면 객체를 불변(Immutable)으로 만들어라.
```java
public class User {
    private String name;

    public void setName(String name) {
        this.name = name;
    }
}
```
```java
public final class User {

    private final String name;

    public User(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}
```
```java
User user = new User("Kim");
// user.setName("Lee"); // 불가능
```
> Setter를 줄이고, 객체의 변경 가능성을 최소화하여 안전하고 예측 가능한 객체를 만들자.

## Item 18. 상속(Inheritance)보다 컴포지션(Composition)을 우선하라

상속을 언제쓰는게 좋을까?
정말 IS-A 관계일 때. (포함 관계)
```java
abstract class AssetExcelRowDto
```
```java
class BasicAssetRowDto extends AssetExcelRowDto
class TasAssetRowDto extends AssetExcelRowDto
class CloudAssetRowDto extends AssetExcelRowDto
```

실무에서는 `extends`를 쓰기 전에 `private final`로 해결 가능한지 먼저 생각하자

대표적인 예제 (결과는 6)
```java
public class InstrumentedHashSet<E> extends HashSet<E> {

    private int addCount = 0;

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }

    public int getAddCount() {
        return addCount;
    }
}
```
```java
InstrumentedHashSet<String> set = new InstrumentedHashSet<>();
set.addAll(List.of("A", "B", "C"));
System.out.println(set.getAddCount());
```

컴포지션으로 바꾸면 (결과는 3)
```java
public class InstrumentedSet<E> implements Set<E> {

    private final Set<E> set;
    private int addCount = 0;

    public InstrumentedSet(Set<E> set) {
        this.set = set;
    }

    @Override
    public boolean add(E e) {
        addCount++;
        return set.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return set.addAll(c);
    }

    public int getAddCount() {
        return addCount;
    }

    // 나머지 Set 메서드는 set에 위임
}
```
```java
Set<String> hashSet = new HashSet<>();
InstrumentedSet<String> set = new InstrumentedSet<>(hashSet);
set.addAll(List.of("A", "B", "C"));
System.out.println(set.getAddCount());
```

> - 코드 재사용 목적이라면 상속부터 하지 말고 컴포지션을 먼저 검토하자.
> - 상속은 부모 클래스의 구현에 강하게 결합되어 예상치 못한 변경 영향이 발생할 수 있다.
> - 컴포지션은 공개된 인터페이스(역할)에 의존하므로 변경에 더 유연하다.
> - 단, 상속이 나쁜 것은 아니다. 명확한 IS-A 관계가 성립하는 경우에는 상속이 더 자연스럽고 효과적일 수 있다.

## Item 19. 상속을 고려해 설계하고 문서화하라. 그러지 않았다면 상속을 금지하라

상속을 허용할 것이 아니라면 `final`로 막자
```java
public final class Car {

    public void move() {
        System.out.println("이동");
    }
}
```
> 상속을 고려해서 설계한 클래스가 아니라면 `final`을 사용하는 것이 안전하다.

## Item 20. 추상 클래스보다는 인터페이스를 우선하라

Java 8 이후 인터페이스에 `default method` 가 생겼다
```java
public interface Animal {

    void move();

    default void eat() {
        System.out.println("먹는다");
    }
}
```
이제 인터페이스도 어느정도 공통 구현을 가질 수 있게 되었고, 추상 클래스의 장점이 많이 줄었다.

### 인터페이스의 장점
다중 구현이 가능 하다
```java
class Dog implements Animal, Serializable, Comparable<Dog>
```
그에 반면, 상속은 한번하면 끝이다

```java
class Dog extends Animal
```
그리고 인터페이스는 훨씬 유연하다

```
Asset
 ├─ ServerAsset
 ├─ CloudAsset
 └─ TasAsset
```
```
class CloudAsset
        implements Exportable,
                   Validatable,
                   Auditable {
}
```
같은 계층을 강요하는 상속과 달리 인터페이스는 필요한 기능만 조합이 가능하다

### 그래도, 추상클래스를 쓰면 좋은 경우?
공통 상태(state)를 가지면 추상 클래스가 좋고,
__템플릿 메서드 패턴__ 에서는 추상클래스가 여전히 강한 영역이다.
```java
abstract class Asset {

    protected Long id;
    protected String name;

    public Long getId() {
        return id;
    }
}
```
이런 경우 인스턴스는 상태를 저장하는 필드를 가질 수 없다

### 가장 권장하는 구조
상황에 맞게 유연하게 설계하자
전혀 다른 구현도 추가하기 쉽다
```java
public abstract class AbstractAssetSheetParser
        implements AssetSheetParser {
}
```
```java
class CloudParser extends AbstractAssetSheetParser
```
```java
class FastCloudParser implements AssetSheetParser
```


> 타입을 정의할 때는 인터페이스를 먼저 만들고, 공통 구현이 필요할 때만 추상 클래스를 추가하라. 
> 인터페이스는 다중 구현이 가능하고 확장성이 뛰어나다.
> 추상클래스는 인터페이스 메서드를 전부 구현하지 않아도 된다.대신 그 책임이 자식 클래스로 넘어간다.

## Item 21. 인터페이스는 구현하는 쪽을 생각해 설계하라

구현체를 생각한 인터페이스와 아닌 인터페이스를 알아보자

### 올바른 interface 예시 (default)

작은 편의 기능 정도는 괜찮다
```java
public interface AssetExcelRow {

    String getIp();

    default boolean hasIp() {
        return getIp() != null
            && !getIp().isBlank();
    }
}
```

### 안좋은 interface 예시 (default)
```java
public interface AssetSheetParser {
    AssetExcelRowDto parse(Row row);
    void validate(AssetExcelRowDto dto);
    default AssetExcelRowDto parseAndValidate(Row row) {
        AssetExcelRowDto dto = parse(row);
        validate(dto);
        return dto;
    }
}
```

인터페이스가 구현 세부사항과 비즈니스 흐름을 소유하기 시작하게되면, 요구사항이 바뀌는 경우 전체 구현체에게 영향을 줌 (OCP 위반)

```java
public abstract class AbstractAssetSheetParser
        implements AssetSheetParser {

    @Override
    public final AssetExcelRowDto parse(Row row) {
        AssetExcelRowDto dto = doParse(row);
        validate(dto);
        return dto;
    }

    protected abstract AssetExcelRowDto doParse(Row row);
    protected abstract void validate(AssetExcelRowDto dto);
}
```
이럴땐 차라리 추상클래스를 사이에 끼우는게 좋다

### 올바른 interface 예시
Parser가 반드시 해야 하는 일만 보인다.
```java
public interface AssetSheetParser {
    AssetExcelSheet supportSheet();
    AssetExcelRowDto parse(Row row, Map<AssetExcelColumn, Integer> columnMap);
}
```

### 안좋은 interface 예시
Parser가 안해도 되는 책임까지 가지고있음 (저장과 로그)
```java
public interface AssetSheetParser {
    AssetExcelSheet supportSheet();
    AssetExcelRowDto parse(Row row, Map<AssetExcelColumn, Integer> columnMap);

    void validateRequiredFields();
    void validateBusinessRule();
    void saveTempData();
    void writeLog();
    void increaseMetric();
}
```

> 인터페이스는 “구현체들이 반드시 지켜야 하는 최소 계약” 만 가져야 한다. 그렇지 않을 경우 OCP원칙을 위반하게 된다

## Item 24. 멤버 클래스는 되도록 static으로 만들라

아래의 코드는 겉으로 보기에는 그냥 `Engine`클래스가 하나 있는 것 처럼 보인다.

```java
public class Car {

    class Engine {
    }
}
```

그런데 자바는 실제로 이렇게 만들어 버린다.
```java
public class Engine {

    private Car car;   // 몰래 추가됨
}
```

위와 같은 상황이 왜 나오는지?
혼자 존재할 수 있지만, "논리적으로 바깥 클래스에만 속하는 클래스"라서 `inner class`로 만드는 경우

`private static class` 
- `private` : 밖에서는 못씀
- `static` : 바깥 클래스의 인스턴스에는 의존하지 않음


### 실무에서 기억할 기준
- 여러 클래스가 사용할 예정 → 별도 `.java` 파일
- 딱 한 클래스 내부에서만 쓰는 작은 보조 타입 → `private static class`
- 바깥 클래스의 필드/메서드를 직접 사용해야 함 → `private class (non-static)`

> Spring실무에서는 `private class`(non-static inner class)를 정말 보기 드물고, 대부분은 별도 파일 아니면 `private static class`를 사용한다고 생각하면 된다.
